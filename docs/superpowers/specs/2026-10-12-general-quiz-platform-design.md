# 通用多游戏问答平台架构设计

日期：2026-10-12

## 目标与边界

将当前单活动答题程序改为同一部署可同时承办多个独立游戏的平台。游戏创建者通过空白表单配置主题、报名字段、轮次、题目、分数和可选抽奖；玩家通过某场游戏的链接参加。新平台的默认数据、题库、图片、页面、文案与部署说明均不包含 X-Lab 专属内容，也不内置该活动的模板。

优先在个人电脑上以尽量零托管费用的方式运行。容量目标是同时 5 场、每场 2,000 人；约 10,000 人在同一秒发起交卷，在指定硬件与实际对外网络入口上，所有**已到达服务端的有效请求**须在 5 秒内得到数据库持久化回执。该目标是上线验收门槛，不是对任意电脑、网络或免费隧道的无条件保证。浏览器点击时间不是服务器截止依据。

首期仅支持组织者配置的客观问答：单选、多选、标准答案填空，以及按字数范围自动计分的开放填写；不提供主观 AI 判分、任意脚本、跨游戏团队战或组织者任意修改正在进行的轮次。抽奖为可选模块。

## 拆分与交付顺序

这是多个相互依赖的子项目，不作为一次大提交交付：

1. **平台基础与数据迁移**：一致性存档旧 SQLite，建立全新 PostgreSQL 数据库、迁移机制、受限连接池、组织者/游戏身份和租户作用域；先让原有核心交卷语义在新的隔离模型上通过测试。
2. **通用配置与前台**：从空白创建游戏；组织者配置和发布；动态报名、题目、计分及玩家页面；移除所有活动专属代码、素材和内容。
3. **可选抽奖与像素风 UI**：通用奖品和权重策略、冻结/审计；玩家、组织者及大屏响应式界面，字体和资产许可。
4. **并发与上线验收**：突发写入、状态分发、压测、故障演练、网络入口及静态资源容量。每个阶段有独立测试与回滚点，最后一阶段未达标不得宣传万人容量。

本设计定义整体接口与边界；实施计划应按上述顺序分段展开。旧数据库不自动导入新平台。

## 身份、权限与游戏配置

平台维护者在本机初始化首个管理员，由其创建或邀请组织者。组织者可创建游戏，并邀请该游戏的其他操作者；所有管理操作记录操作者、游戏、时间和理由。普通玩家仅从单场专属链接注册和作答，身份、会话及成绩按游戏独立，不提供跨游戏玩家档案。管理员权限不由登录某场玩家账号获得。

组织者先保存草稿，再在“名称与介绍 → 报名字段 → 轮次与时长 → 题目与计分 → 榜单及可选抽奖 → 预览发布”的向导中配置。报名字段支持文本和有限选项及必填设置；昵称/展示名是最低限度的玩家显示字段，真实姓名不是平台默认必填。配置采用受校验的数据结构，不执行用户编写的 JavaScript、SQL 或 CSS。题目类型分别配置选项与正确项、接受的规范化文本答案，或回答长度范围；每题分值是非负整数。组织者可设置轮次的题数与时长，不预设四轮、30 题或固定 300 秒。

发布前校验题目、答案、时长、分值与抽奖配置，生成游戏专属链接。已开始轮次使用其启动时锁定的规则及题目版本；不得无记录地改题或改分。开始只由该游戏授权操作者手动触发，数据库事务保证单轮只启动一次；截止采用数据库保存的实际开始时间加该轮时长。已发布的成绩/答案才在玩家端展示。错题作废、资格或加分更正走受授权的事务、重算与审计，不直接修改汇总分。

同一游戏中可使用自定义的奖品顺序和“等概率”或“积分加权”策略。后者使用明示的基础权重、每档积分换算与每人中奖上限，冻结时生成带哈希的名单、规则版本和整数权重；用安全随机源抽取，先持久化结果再展示，重试返回原结果。奖品及资格更正留痕。未启用抽奖的游戏不展示奖池操作。

## 数据与服务边界

本机安装 PostgreSQL，应用通过异步数据库客户端和有限连接池访问；数据库只监听可信本机接口，不直接向玩家开放。HTTP 并发连接数不等于数据库连接数。应用可运行多个 Node 工作进程，共享数据库、配置及游戏状态，不以任一进程内存为持久化事实。首期不依赖 Redis 或付费消息队列；连接池大小、工作进程数和查询索引以目标硬件压测调整。

主要实体包括：`organizers`、`games`、`game_members`、`game_versions`、`rounds`、`questions`、`players`、`player_sessions`、`drafts`、`submissions`、`round_scores`、`bonus_events`、`eligibility`、`prizes`、`freeze_snapshots`、`draws`、`audit_events`。所有参与游戏的表都带 `game_id`；关联、唯一键与查询必须校验游戏作用域。数据访问集中于带明确 `gameId` 参数的存储层，服务端每次校验玩家所属游戏、组织者成员身份和权限；针对跨游戏猜测 ID 的读取及修改编写拒绝测试。敏感报名字段不进入公开榜单，默认只显示展示名及必要的消歧标识。

提交接收链路为：读取完整且受大小限制的请求体，记录服务器收到完整请求的时刻，校验游戏身份和实际截止时刻，在数据库事务中按 `(game_id, player_id, round_id, request_key)` 幂等持久化答卷，**事务提交后**才返回回执。相同请求键和相同内容返回原回执；相同键不同内容报冲突。截止后到达的新答卷被拒绝，截止前到达但仍在处理中的请求可以完成持久化；该轮必须等这些请求处理结束再结算。进程在提交前崩溃的请求没有成功回执，不能被称作已接收。

结算以数据库中的最终有效提交为准，按轮次和版本一次性、可恢复地计分和发布；多进程调度采用数据库协调，避免重复结算。数据库提交路径不执行同步密码哈希、同步大文件读取或全场榜单重算。密码运算移出事件循环；排名在公布或有效更正后计算并缓存该场快照。玩家端用服务器起止时间显示本地倒计时，通过轻量状态通知获知开轮、公布和开奖；断线重连补拉快照，通知不可用时采用抖动退避轮询。草稿保存限频，不再每次敲字都写库，且草稿永远不等于成功交卷。

## 像素视觉与中文

采用 NES.css 的像素组件样式，不修改其源码；以自定义布局构成组织者填写向导、玩家答题页及大屏。自托管 Fusion Pixel Font 的 12px、proportional、zh-Hans WOFF2 版本，作为短标题、按钮、菜单和状态标签的中英文字体；长段说明、复杂输入及题干可使用普通中文字体提升可读性。CSS 覆盖放在 NES.css 后面，只对相应组件应用整数倍基准字号；不能把 `body` 一律设置为 24px 导致手机表单拥挤。保留缺字回退，测试生僻姓名、繁体、标点、数字、不同缩放倍率以及长题干。

字体作为版本化静态资源缓存，按实际字形需求优化传输，不能仅裁剪固定文案而导致用户输入缺字；新玩家集中打开页面时也要测试资产交付容量。保留 NES.css 与额外字体各自的许可及所需版权文件，衍生字体处理遵守其许可证。手机 320px 起无横向滚动，触控目标和倒计时/回执清晰可见；大屏按 16:9 验收，尊重减少动态效果设置。游戏创建者可填写标题、主色和封面，但不能注入代码或无约束样式。

## 部署、安全与旧数据

公网入口若经隧道/代理，必须在端到端压测中覆盖该实际入口；免费服务是否允许目标连接数、吞吐量及自定义域名需以真实部署验证，不假定套餐能力。站点与 API 同源，服务端校验 HTTPS 来源，管理和玩家会话隔离，使用安全 Cookie、限流及审计。静态资产可通过缓存层卸载，但不得使答题 API 变成无鉴权的跨域接口。运行电脑持续供电、防休眠，数据库和应用自启动；备份在独立介质，并演练恢复。磁盘损坏时只能恢复到最后一次有效异地/离机备份，不能把本机另一份文件称为容灾。

现有 `data/` 中的旧 SQLite 数据先通过一致性备份生成受保护的**独立存档**，验证完整性、数量和校验和；新 PostgreSQL 使用独立目录与全新空库，不导入旧玩家、题目、奖品和成绩。旧数据库及存档在未明确保存期和恢复方案前不删除，改造代码不覆盖旧库。完成新平台的通用测试后再清理仓库中的原活动文案、图片、旧部署配置和仅针对旧活动的夹具；通用行为测试应替换为无品牌的新用例。

## 验收与故障语义

功能测试覆盖两名组织者、五场游戏的读写隔离、动态轮次数量和时长、四类题型、手动开轮、截止前后并发、幂等重试、结算恢复、审计、可选抽奖和未公开答案保护。迁移测试验证旧 SQLite 存档可恢复、新空库不显示旧数据；页面测试覆盖手机、电脑和大屏，中文字体加载失败时仍能完成交卷。

压测在目标电脑上，使用**多台发压机器**经实际对外入口进行：预先完成有效报名/登录，同时打开五场各 2,000 个玩家会话；在一秒窗口发起 10,000 次不同玩家的完整交卷请求，记录客户端到服务端响应的最慢时间。合格条件是所有有效请求均获得数据库持久化回执且不超过 5 秒，答卷唯一、无串场，确认后重试与重启均不丢失。另行测量首屏静态资源、状态通知、管理开轮、计分/排名公布以及数据库备份对峰值的影响，重复测试并记录电脑规格、网络、版本及报告。截止公平性测试以**完整请求到达服务端**为准；浏览器在截止前点击但网络延迟到截止后才到达，不被伪称为准时交卷。

若出现排队溢出、磁盘不可用、代理限流或超过 5 秒，系统给出明确的失败/未确认状态及可追踪日志；不能返回虚假的成功回执，也不得宣布达到万人目标。容量不达标时采取降低单机承诺、改善网络入口或升级资源的显式决策，不静默改变游戏规则。
